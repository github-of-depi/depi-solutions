## Как строить эффективный процесс code review?

1. **Маленькие PR** — <400 строк, одна задача
2. **Self-review** перед запросом review
3. **Описание PR**: что изменилось и почему, скриншоты для UI
4. **Время**: review в течение 1 рабочего дня
5. **LGTM criteria**: чёткие ожидания (2 approvals, CI green)

## Что проверять специфически для React/TypeScript кода?

**React**: бесконечные циклы (useEffect зависимости), утечки памяти (cleanup), key prop, memo/callback стабильность. **TypeScript**: `any` без обоснования, type assertions, nullable safety, generic constraints. **Performance**: лишние ре-рендеры, тяжёлые вычисления без мемоизации.

## Как review большие PR?

1. Начать с description и тестов — понять намерение
2. Просмотреть изменения по файлам, не diff stream
3. Выявить паттерн — не комментировать каждый экземпляр одной проблемы
4. High-level комментарий если архитектурная проблема
5. Предложить разбить на несколько PR если слишком большой

## Что такое conventional comments?

Префиксы для классификации комментариев:

- `[blocker]` — нужно исправить до merge
- `[nitpick]` — мелочь, можно проигнорировать
- `[question]` — уточнить намерение
- `[suggestion]` — идея, не требование
- `[praise]` — позитивный фидбек
