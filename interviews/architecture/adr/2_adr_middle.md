## Как писать ADR?

Стандартная структура (MADR формат):

```markdown
# ADR-001: Использование TanStack Query для серверного состояния

## Статус
Принято

## Контекст
Приложение делает множество API запросов. useEffect + useState порождает boilerplate и баги.

## Рассмотренные варианты
1. TanStack Query — caching, invalidation, devtools
2. RTK Query — интеграция с Redux
3. SWR — проще, меньше возможностей

## Решение
TanStack Query — лучший баланс возможностей и простоты.

## Последствия
+ Автоматическое кэширование и ре-фетч
+ Отличные devtools
- Ещё одна зависимость
- Команда должна изучить API
```

---

## Когда создавать ADR?

Создавать при решениях, которые:
- Сложно изменить позже (выбор стека, базы данных)
- Затрагивают несколько команд
- Отличаются от общепринятых практик
- Были предметом споров

НЕ создавать для: тривиальных решений, реализационных деталей.

---

## Какие форматы ADR существуют?

- **MADR** (Markdown Architectural Decision Records) — популярный, структурированный
- **Nygard** (Майкл Найгард) — оригинальный минималистичный формат
- **Y-Statements** — "В контексте X, столкнувшись с Y, мы решили Z, достигая Q, принимая риск R"

---

## Как хранить и версионировать ADR?

В репозитории, рядом с кодом (`docs/adr/`). Нумерация: `ADR-001-use-tanstack-query.md`. Статусы: `proposed → accepted / rejected / deprecated / superseded`. При пересмотре: не редактировать старый ADR, создавать новый со ссылкой.
