## Как работает HTTP кэширование — ETag и Cache-Control?

`Cache-Control: max-age=3600` — кэшировать 1 час, без запроса. `ETag: "abc123"` — fingerprint ресурса. При повторном запросе: `If-None-Match: "abc123"` → сервер возвращает `304 Not Modified` без тела. `stale-while-revalidate`: отдать кэш, обновить в фоне — лучший UX.

## Как проектировать REST API с точки зрения фронтенда?

1. **Версионирование**: `/api/v1/` — для обратной совместимости
2. **Консистентные ошибки**: `{ error: { code, message, details } }`
3. **Pagination**: cursor-based для бесконечной прокрутки
4. **Sparse fieldsets**: `?fields=id,name` — только нужные поля
5. **Nesting**: максимум 2 уровня (`/users/1/orders`) — глубже через query params

## Что такое Rate Limiting и как его обрабатывать?

Rate Limiting — ограничение количества запросов. Сервер возвращает `429 Too Many Requests` с `Retry-After: 30` заголовком. Обработка: exponential backoff + jitter, показ пользователю сообщения, очередь запросов.

## Как работает HTTP/2 и что он даёт?

HTTP/2: мультиплексирование (несколько запросов в одном TCP соединении), бинарный протокол, сжатие заголовков (HPACK), server push. Устраняет head-of-line blocking HTTP/1. HTTP/3 (QUIC) — поверх UDP, ещё быстрее на ненадёжных соединениях.

## Что такое BFF (Backend for Frontend)?

## Как реализовать optimistic updates с REST API?

Немедленно обновить UI, параллельно отправить запрос. При ошибке — откатить. TanStack Query `onMutate`/`onError`/`onSettled` — стандартный паттерн.

```typescript
const mutation = useMutation({
  mutationFn: toggleTodo,
  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ["todos"] });
    const prev = queryClient.getQueryData<Todo[]>(["todos"]);
    queryClient.setQueryData(["todos"], (old: Todo[]) =>
      old.map(t => t.id === id ? { ...t, done: !t.done } : t)
    );
    return { prev };
  },
  onError: (_, __, ctx) => queryClient.setQueryData(["todos"], ctx?.prev),
  onSettled: () => queryClient.invalidateQueries({ queryKey: ["todos"] }),
});
```

## Оптимизация HTTP?

**Сократить количество запросов:**
- HTTP/2 мультиплексирование (несколько запросов в одном соединении)
- Бандлинг ресурсов, спрайты, инлайн критического CSS
- Prefetch/preconnect для предварительного установления соединений

**Уменьшить размер:**
- Gzip/Brotli сжатие (`Content-Encoding: br`)
- Минификация CSS/JS/HTML
- Оптимизация изображений (WebP, AVIF), `srcset`

**Кэшировать агрессивно:**
- `Cache-Control: max-age=31536000, immutable` для хэшированных ресурсов
- `stale-while-revalidate` для частично динамических данных
- CDN для статики

**Ускорить соединение:**
- Keep-Alive (HTTP/1.1)
- `dns-prefetch`, `preconnect` для внешних доменов
- HTTP/3 (QUIC) для нестабильных сетей

## Микросервисная архитектура?

**Микросервисы** — архитектурный подход, при котором приложение разбивается на небольшие независимые сервисы, каждый отвечает за одну бизнес-функцию.

**Характеристики:**
- Независимое развёртывание каждого сервиса
- Изоляция данных (своя база у каждого)
- Коммуникация через API (REST, gRPC, события)

**Плюсы:** масштабируемость отдельных частей, технологическая гибкость, отказоустойчивость (один сервис падает — другие работают).

**Минусы:** сложность инфраструктуры, сетевые задержки, distributed tracing, eventual consistency.

**Для фронтенда:** micro-frontends — аналогичный подход для UI; BFF (Backend for Frontend) — агрегирующий gateway для клиентских нужд.

## TLS и REST?

**TLS** (Transport Layer Security) — криптографический протокол, обеспечивающий шифрование, аутентификацию и целостность данных. HTTPS = HTTP + TLS.

REST API должны всегда работать через HTTPS (TLS 1.2+). TLS и REST — ортогональны: TLS защищает транспорт, REST описывает интерфейс. Можно и нужно использовать оба.

**TLS Handshake:** клиент предлагает cipher suites → сервер выбирает + присылает сертификат → клиент проверяет сертификат (Certificate Authority) → обмен ключами → шифрованное соединение.

**mTLS** (mutual TLS) — клиент тоже предъявляет сертификат: используется для аутентификации сервис-к-сервису в микросервисах.

## Безопасность REST API?

**Аутентификация и авторизация:**
- JWT + httpOnly cookie (защита от XSS)
- OAuth 2.0 для сторонних сервисов
- API-ключи для server-to-server

**Защита от атак:**
```
HTTPS everywhere                — шифрование трафика
CORS: конкретные origin         — не wildcard '*' в prod
Rate limiting (429)             — защита от brute force/DDoS
Input validation                — предотвращение injection
Content-Security-Policy         — защита от XSS
CSRF: SameSite cookie           — защита от CSRF атак
```

**Дополнительно:**
- Не возвращать стектрейс в ошибках 500
- Версионирование API (`/v1/`) — плавная миграция
- Логирование подозрительных запросов
- `Helmet.js` (Node.js) — набор защитных заголовков
