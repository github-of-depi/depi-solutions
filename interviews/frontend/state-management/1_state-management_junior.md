## Зачем нужны менеджеры состояния?

По мере роста приложения состояние начинает использоваться в компонентах далеко друг от друга. Поднятие состояния наверх (lifting state up) приводит к props drilling. Менеджеры состояния централизуют данные, делают их доступными в любой части дерева и обеспечивают предсказуемые обновления.

## Что такое props drilling и как его избежать?

Props drilling — передача данных через несколько промежуточных компонентов, которые сами эти данные не используют. Решения: Context API (встроен в React), Zustand/Redux (внешние сторы), composition (дети как props).

```typescript
// Проблема
<A user={user}><B user={user}><C user={user} /></B></A>

// Решение через Context
const UserContext = createContext<User | null>(null);
function C() { const user = useContext(UserContext); }
```

## Что такое Redux и какова его основная идея?

Redux — предсказуемый контейнер состояния на основе трёх принципов: одно дерево состояния (single source of truth), состояние только для чтения (изменяется через actions), изменения через чистые функции (reducers). Redux Toolkit — официальный способ писать Redux с меньшим boilerplate.

## Что такое Zustand?

Zustand — минималистичный менеджер состояния. Стор создаётся как хук, нет boilerplate как в Redux, нет Provider-а. Подходит для большинства средних приложений. Набирает популярность как замена Redux для небольших и средних проектов.

```typescript
import { create } from "zustand";
const useStore = create<{ count: number; inc: () => void }>(set => ({
  count: 0,
  inc: () => set(state => ({ count: state.count + 1 })),
}));
function Counter() {
  const { count, inc } = useStore();
  return <button onClick={inc}>{count}</button>;
}
```

## В чём разница между клиентским и серверным состоянием?

**Клиентское состояние** — UI state: открыт ли дропдаун, текущая вкладка, данные формы. Управляется React state/Zustand/Redux. **Серверное состояние** — данные с сервера: список пользователей, данные продукта. Требует кэширования, синхронизации, обработки loading/error. Управляется TanStack Query, RTK Query или SWR.

## Когда достаточно useState, а когда нужен менеджер состояния?

`useState` достаточно для: локального UI-состояния компонента, данных одного экрана без шаринга. Менеджер состояния нужен, когда: состояние нужно в 3+ несвязанных компонентах, нужна история изменений/DevTools, состояние переживает unmount компонента.
