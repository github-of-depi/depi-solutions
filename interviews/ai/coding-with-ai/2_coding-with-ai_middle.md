## Как предотвратить «жульничество» ИИ с тестами?

Основной метод — **TDD** с циклом «красный → зелёный → рефакторинг». Проблема: ИИ иногда не исправляет код, а меняет условие теста, чтобы он прошёл (например, меняет «неделя начинается с понедельника» на «с воскресенья»).

Практические меры защиты:
1. **Запретить изменение тестов** явно в системном промпте: «Ты не можешь изменять файлы `*.test.ts` без моего явного разрешения»
2. **CI-хук**: блокировать PR, в котором изменены тестовые файлы, если это не ожидается
3. **Проверять diff вручную**: в Cursor/Claude Code всегда просматривать `git diff` перед принятием изменений
4. **Разделять задачи**: сначала написать тест (вы), потом попросить ИИ сделать его зелёным

```typescript
// В .cursorrules / system prompt агента:
// "ВАЖНО: Никогда не изменяй файлы с суффиксом .test.ts или .spec.ts.
// Если тест не проходит — исправляй реализацию, а не тест."
```

Даже при TDD контроль остаётся за человеком — ИИ ускоряет, но не отменяет ревью.

## Как экономить контекст при работе с большой кодовой базой?

Главный принцип — давать агенту ровно ту часть системы, которая нужна для конкретного изменения. Модель не должна «читать» весь проект ради правки одного метода.

Практические приёмы:

1. **Формулируйте задачу узко**: «Измени валидацию только в `src/auth/validator.ts`» вместо «улучши авторизацию»
2. **Предсказуемая структура**: ясные имена файлов, однозначные пути — агент быстрее находит нужное
3. **Краткая «карта проекта»** в системном промпте или `ARCHITECTURE.md`: 10–20 строк об основных модулях
4. **Фиксируйте правила отдельно** (`.cursorrules`, `AGENTS.md`) — они подгружаются автоматически, не занимая контекст диалога
5. **Разделяйте фазы**: сначала попросите агента только найти нужные файлы, потом — понять код, потом — изменить

```
ARCHITECTURE.md (пример карты):
- src/auth/       → авторизация (JWT, refresh tokens)
- src/api/        → Express-роуты, только координация
- src/services/   → бизнес-логика, зависимости через DI
- src/db/         → Prisma-репозитории, без бизнес-логики
```

## Как правильно работать с Git при использовании ИИ?

**Коммитьте чаще** — это «сохранения» от внезапных ошибок ИИ. Если агент «сломал» что-то несколько шагов назад, вы сможете откатиться. Размер коммита — одна логическая единица изменений.

Ключевые правила:
- **Сообщения коммитов**: поручайте писать ИИ, но проверяйте — они обычно хорошие, но иногда расплывчатые
- **Ветвление**: не доверяйте агенту самостоятельно управлять ветками и слияниями — были случаи потери кода из-за невмёрженных веток
- **Перед крупными изменениями**: `git stash` или новая ветка — агент должен работать на чистом рабочем дереве
- **Git worktrees**: полезны, когда два агента работают параллельно над разными задачами без конфликтов

```bash
# Полезная привычка: проверить diff перед принятием изменений агента
git diff --stat
git diff src/auth/

# Откат до последнего «сохранения»
git checkout -- .
git stash pop
```

## Что такое SDD и зачем нужны спецификации при работе с ИИ?

**SDD (Spec-Driven Development)** — подход, при котором спецификация находится во главе угла: сначала фиксируются требования и архитектура письменно, затем ИИ генерирует код строго по ним. Это противоположность вайбкодингу.

Почему ИИ без спецификаций ненадёжен:
- **Каждый новый диалог** — чистый лист: модель не помнит устных договорённостей
- **Контекст ограничен**: при длинных сессиях детали теряются через compaction
- **Интерпретация неоднозначных требований** различается от запуска к запуску

Что фиксировать в спецификации:
- Требования и архитектурные правила (`SPEC.md`, `ARCHITECTURE.md`)
- Соглашения по стилю кода (`.cursorrules`, `AGENTS.md`)
- ADR — решения и их причины (см. `interviews/architecture/adr/`)
- Сценарии поведения и API-контракты

```markdown
# SPEC.md (минимальный пример)

## Правила архитектуры
- Бизнес-логика только в `src/services/`
- Роуты не содержат логики, только вызовы сервисов
- Все внешние зависимости инжектируются через DI

## Стиль кода
- TypeScript strict mode
- Никаких `any`
- Асинхронный код только через `async/await`
```

## Какие SDD-фреймворки существуют и чем они отличаются?

SDD-фреймворки вводят строгий workflow: **спецификация → план → задачи → код**. Они решают проблему «ИИ в больших проектах» через структуру и «память» о решениях.

| Фреймворк | Звёзды | Для кого | Суть |
|-----------|--------|----------|------|
| **Spec-Kit** | ~63k | Команды, крупные проекты | «Лучший и правильный» SDD, полноценный workflow |
| **OpenSpec** | ~17k | Старт с SDD, соло/маленькие команды | Простой, легковесный, классический Spec-Driven |
| **BMAD** | ~30k | — | Пытается совместить SDD с Agile — слишком сложный |
| **Kiro** | — | Те, кто не привязан к IDE | AI IDE от Amazon с нативным SDD в интерфейсе |

**Рекомендация:**
- Начинаете с SDD → **OpenSpec** (простой вход)
- Команда и серьёзный проект → **Spec-Kit**
- Готовы сменить IDE → **Kiro** (Amazon) — SDD встроен, разные фазы в одном окне
- **BMAD** не рекомендуется: слишком много концепций при сомнительной пользе от Agile-слоя

## Что такое Cursor Memory Bank и Task Master?

Это инструменты для управления «памятью» агента между сессиями — каждый решает разную проблему.

**Cursor Memory Bank** — система сохранения контекста о решениях и структуре проекта. Контекст не теряется при переключении между задачами: сохраняется в специальных Markdown-файлах (`projectbrief.md`, `activeContext.md` и др.) и подгружается динамически по мере необходимости. Снижает повторение архитектурных ошибок.

**Task Master** — инструмент, который разбивает написанный вами PRD (Product Requirements Document) на задачи и отслеживает их выполнение с помощью отдельной модели. Экономит контекст, сохраняет фокус агента на текущей задаче.

```
Memory Bank структура:
memory-bank/
  projectbrief.md      → суть проекта и цели
  systemPatterns.md    → архитектурные паттерны и решения
  activeContext.md     → текущая задача и её контекст
  progress.md          → что сделано, что в работе
```

**Когда использовать:**
- Memory Bank → всегда, даже для небольших проектов
- Task Master → крупный проект, длинная работа агента без полного SDD-фреймворка

## Что такое self-review в AI-разработке?

**Self-review** — этап, когда разработчик перед отправкой кода на внешнее ревью сам проходит по чеклисту: запускает автотесты, сверяет реализацию с макетами (Figma), проверяет соответствие спецификации. В AI-разработке к этому добавляется проверка, что ИИ не «сошёл с курса»: не нарушил архитектурные правила, не изменил тесты, не добавил лишнего.

**Формализованный self-review с AI:**
1. `git diff` — проверить все изменения
2. Запустить тесты: `npm test`
3. Попросить ИИ: «Проверь, всё ли соответствует спецификации в `SPEC.md`»
4. Сверить визуал с Figma (для UI-задач)
5. Прикрепить план задачи к тикету — человек-ревьюер видит не только код, но и логику принятых решений

Это ускоряет внешнее ревью и повышает его качество: ревьюер понимает намерение, а не угадывает его из кода.

## Какой реальный прирост производительности даёт ИИ?

По данным реальных команд (2024–2025): чистый прирост составляет **10–30%** с учётом затрат на обучение, поддержку инфраструктуры и дополнительные ревью. Для прототипов и небольших задач прирост выше (×2–3), для сложных enterprise-систем — скромнее из-за затрат на контроль качества.

Важные оговорки:
- **Требования к разработчикам выросли**: нужно не только писать код, но и формулировать задачи, читать и ревьюить AI-код, управлять контекстом
- **Не все задачи ускоряются одинаково**: рутинный CRUD, написание тестов, бойлерплейт → ×3–5; сложная бизнес-логика → ×1.2–1.5
- **Накопленный технический долг** AI-кода без должного ревью может замедлить команду через 3–6 месяцев
- ИИ становится новым **профессиональным стандартом**, а не временным преимуществом
